# Apple Push Notification service (APNs) Research & Technical Evaluation

## Context & Objectives

Milestone **M9 (APNs / iOS Native Integration)** connects the server-side state observation engine (Server Companion) to the user's iPhone via Apple Push Notification service (APNs).
This document reviews the official Apple specifications, token-based provider authentication, APNs HTTP/2 protocol, payload constraints, error classification, and mobile lifecycle rules.

---

## 1. APNs Architecture & Trust Boundaries

The push notification pipeline spans four distinct trust boundaries:

```
┌────────────────────────┐         ┌────────────────────────┐
│  Server Companion      │         │   AgentDeck Push Relay │
│  (Managed Linux Host)  │         │   (Central Gateway)    │
│                        │         │                        │
│  - Observes tmux/git   │ Outbound│  - Device Registry     │
│  - Zero secrets/APNs   ├────────►│  - APNs AuthKey (.p8)  │
│  - Outbox retry queue  │  HTTPS  │  - ES256 JWT Generator │
└────────────────────────┘         └───────────┬────────────┘
                                               │
                                               │ HTTP/2 Mutual TLS / Token Auth
                                               ▼
                                   ┌────────────────────────┐
                                   │   Apple APNs Gateway   │
                                   │   (api.push.apple.com) │
                                   └───────────┬────────────┘
                                               │
                                               │ Device-specific secure connection
                                               ▼
                                   ┌────────────────────────┐
                                   │   iPhone (iOS)         │
                                   │   - UserNotifications  │
                                   │   - Lock screen banner │
                                   │   - Deep link tap      │
                                   └────────────────────────┘
```

### Strict Credential Isolation
1. **APNs Authentication Key (`.p8`)**: Stored **strictly in the Push Relay**. Never placed in Git, never bundled in the mobile application, and never deployed to managed Linux servers.
2. **Device Tokens**: Generated by iOS for the specific app + device combination. Sent to the Push Relay upon registration or rotation; never printed to analytics, crash logs, or console output.
3. **Companion Secrets**: Dedicated pre-shared tokens authenticating outbound companion-to-relay event forwarding. Distinct from SSH credentials and APNs keys.

## 2. APNs Provider Authentication (Token-Based)

Apple provides two authentication mechanisms for provider servers:
- **Certificate-Based (`.p12` / Mutual TLS)**: Deprecated in practice; requires yearly certificate renewal per bundle ID.
- **Token-Based (`.p8` / JWT / ES256)**: **Recommended by Apple**. A single 10-year signing key can be used across development and production environments and multiple app bundle IDs.

### JWT Structure (RFC 7519)
- **Header**:
  ```json
  {
    "alg": "ES256",
    "kid": "<10-character Key ID>"
  }
  ```
- **Claims (Payload)**:
  ```json
  {
    "iss": "<10-character Apple Developer Team ID>",
    "iat": 1727200000
  }
  ```
- **Signature**: Generated using ECDSA with P-256 curve and SHA-256 hash algorithm (`ES256`).
- **Token Expiration & Caching**: Apple requires provider tokens to be valid for at least 20 minutes and invalidates them after 60 minutes. The Push Relay must cache tokens and rotate them after **50 minutes** (conservative margin) rather than regenerating on every request.

## 3. APNs HTTP/2 Protocol & Request Headers

### Endpoints
- **Sandbox / Development**: `https://api.sandbox.push.apple.com:443/3/device/<device_token>`
- **Production**: `https://api.push.apple.com:443/3/device/<device_token>`

### Mandatory & Key Headers
| Header | Value | Description |
|---|---|---|
| `:method` | `POST` | Standard HTTP/2 method |
| `:path` | `/3/device/<device_token>` | 64-character hexadecimal device token string |
| `authorization` | `bearer <JWT_TOKEN>` | Provider authentication token |
| `apns-topic` | `<Bundle_ID>` (e.g. `com.agentdeck.app`) | App Bundle Identifier registered with Apple |
| `apns-push-type` | `alert` | Declares notification type (`alert`, `background`, `voip`). **Must be `alert`** for visible user prompts |
| `apns-priority` | `10` (Immediate) or `5` (Power-conserving) | `10` sends immediately; required for `waitingUser` and critical errors |
| `apns-expiration` | `<UNIX_EPOCH_TIMESTAMP>` | Seconds until the message is discarded if the device is offline |
| `apns-collapse-id` | `agent:<instance_id>` | Replaces pending notifications with the same collapse identifier |

## 4. APNs Payload Format & Privacy Modes

### Standard Alert Payload (`aps` Dictionary)
```json
{
  "aps": {
    "alert": {
      "title": "Codex needs your input",
      "subtitle": "Portal Proveedores",
      "body": "Interactive CLI prompt requires your response."
    },
    "sound": "default",
    "badge": 1,
    "category": "AGENT_INTERACTION"
  },
  "agentdeck": {
    "schemaVersion": 1,
    "eventId": "evt_srv_1_1234",
    "type": "agentWaitingUser",
    "severity": "actionRequired",
    "serverId": "srv_1",
    "projectId": "proj_1",
    "destination": {
      "route": "agent_terminal",
      "projectId": "proj_1",
      "serverId": "srv_1",
      "agentInstanceId": "ad_agent_codex_proj_1"
    }
  }
}
```

### Privacy Preview Modes
1. **Full Preview**: Contains project name and agent provider name ("Codex is waiting for input in Portal Proveedores").
2. **Project Only**: Displays project name with generalized description ("AgentDeck action required in Portal Proveedores").
3. **Generic Preview**: Completely anonymized for sensitive lock screens ("AgentDeck requires your attention").

**Strict Exclusion**: Push payloads **never contain** terminal buffers, full prompts, Git diff contents, passwords, API tokens, or server filesystem paths.

## 5. APNs Response Handling & Error Matrix

| HTTP Status | Reason Code | Description | Relay Action |
|---|---|---|---|
| `200` | — | Success (accepted by APNs) | Mark event delivered to APNs |
| `400` | `BadTopic` | Bundle ID mismatch | Log critical configuration error; do not retry |
| `400` | `BadDeviceToken` | Malformed token | Discard request; do not retry |
| `403` | `ExpiredProviderToken` | JWT expired | Invalidate cached JWT, regenerate, and retry |
| `410` | `Unregistered` | App uninstalled or token expired | **Deactivate / disable device registration** |
| `429` | `TooManyRequests` | Rate limit exceeded | Backoff exponentially and retry |
| `500` / `503` | `InternalServerError` / `ServiceUnavailable` | APNs transient issue | Retry with exponential backoff and jitter |

## 6. iOS Native Lifecycle & Integration Patterns

### 1. Contextual Permission Request
Never invoke `UNUserNotificationCenter.requestAuthorization` immediately upon cold start. First present an informative onboarding / settings screen explaining that notifications alert the user when remote background tasks require attention.

### 2. Device Token Lifecycle
- Call `UIApplication.shared.registerForRemoteNotifications()`.
- Receive token in `didRegisterForRemoteNotificationsWithDeviceToken`.
- Transmit token to Push Relay via `POST /v1/devices/register`.
- Token rotation: When iOS provides a new token, the mobile client updates the Push Relay, replacing the previous registration for that installation.

### 3. Notification Tap & Deep Link Handling
- **Terminated (Cold Start)**: `UNUserNotificationCenterDelegate.didReceiveNotificationResponse` caches pending destination payload until Flutter engine and navigation hierarchy are ready, then routes the user directly to the destination view (`TerminalPage`, `GitChangesPage`, `ServerOperationsPage`).
- **Background / Foreground (Warm Start)**: Directly dispatches to the active `NotificationCoordinator` and navigates without reload.
- **Event Reconciliation**: Tapping a notification opens the destination and triggers an immediate catch-up sync with the **Companion Journal** (`agentdeck-companion events --after <cursor>`). The push notification is an ephemeral signal; the companion journal remains the single source of truth.

## 7. Requirement for Physical Device Validation (`PENDING_MACOS_VALIDATION`)

The following capabilities cannot be verified on Windows development environments:
1. Physical Apple Push Notification service token generation (iOS Simulators support mock APNs, but production routing requires a signed physical iPhone).
2. Xcode Code Signing with Apple Developer Team ID and `aps-environment` entitlement.
3. Lock screen visual verification, custom sounds, and native notification actions.
4. Physical device wake-up and cold-start launch benchmarks.
